# DATA NEEDED - PER INSTRUMENT (retailer_db_edge) - 04-11-2026

STATUS: **declared in code, pending live census + Fable + external auditor + Kumar.** Nothing here is proven. Generated by `tools/gen_data_needed_instruments_041126.py` from files in the repo; no box, no database was touched. The CSV is `docs/framework/data_needed_instruments_041126.csv` (183 rows, one per instrument x data product).

Companion, not replacement: `DATA_NEEDED_FOR_EDGE_031126.md` is the group-level list (G1-G14); this file is the per-instrument expansion. Class comes from `config/recoverability.json` (itself still PROPOSED) via `dp_recoverability.effective()`, applied to the store table or day-file name. For day files named `ticks_YYYYMMDD.db` / `upstox_YYYYMMDD.db` the generator substitutes a sample date (20261104) before classifying, because `classify()` on the literal string `upstox_YYYYMMDD.db` returns UNKNOWN (its `upstox_20` pattern needs a real date); the substitution is what makes those 71 rows (every row whose store_table is a `ticks_`/`upstox_`/`depth_`/`tbt_` day-file template) LIVE_ONLY, and the live-file check `tools/check_recoverability_placement.py` classifies real file names, which do carry a date. DECISION (Fable round 2, finding 6): the literal template `upstox_YYYYMMDD.db` is deliberately left UNKNOWN, i.e. protected HDD-only by the fail-safe; adding a bare `upstox_` pattern would also capture recoverable history DBs such as `upstox_current.db`, so the date-bearing `upstox_20` pattern stays and the template is never a real file.
